# ADR-0001: 모듈러 모놀리스로 시작한다

- 상태: 채택
- 날짜: 2026-10-01

## 배경

가족 사진을 모아 월간지로 자동 조판·인쇄하는 서비스를 만든다. 작은 팀이 만들고, 아직 앱 언어와 배포 환경이 정해지지 않았다.
지금까지 설계하며 확인한 사실:

- 호의 상태 전이, 업로드 차단, 마감 배치, 승인 무효화는 **한 트랜잭션 안에서 서로의 데이터를 확인**해야 한다.
  (예: 마감 배치가 호 행을 잠그면 같은 순간의 업로드는 대기했다가 거부된다. 이 보장은 한 DB의 행 잠금에 의존한다.)
- 무거운 계산(조판, 이미지 분석, PDF 렌더)은 있지만, 호당 사진 수십~수백 장·그룹당 월 1회 수준이라 지금은 독립 확장이 급하지 않다.

## 결정

**모듈러 모놀리스**: 하나의 코드베이스와 하나의 DB를 쓰되, 8개 모듈(identity, groups, templates, issues, intake, layout, review, printing)로 나누고 경계를 코드로 강제한다.
무거운 작업은 **같은 코드베이스의 별도 워커 프로세스**로 돌린다.

## 이유

1. **마이크로서비스로 쪼개면 지금의 트랜잭션 보장이 분산 트랜잭션(사가)이 된다.** 위의 업로드/마감 직렬화, "승인 후 수정하면 호가 review로 복귀" 같은 규칙이 모두 복잡해진다.
2. 팀이 작아 서비스별 배포·모니터링·버전 호환 비용을 감당할 이유가 없다.
3. 단, **모놀리스는 경계를 강제하지 않으면 그냥 진흙덩어리가 된다.** 그래서 소유권(T90), 의존 방향(T91), 순환 금지(T92)를 DB 테스트로 CI에서 강제한다.

## 결과 / 감수하는 점

- `issues` 모듈은 호 생명주기를 지휘하므로 다른 모듈의 상태를 확인한다. 이 결합은 의도한 것이며 [architecture.md](../architecture.md)의 "알려진 예외" 표에 기록한다. **함수 수준 결합은 자동 검사가 없다.**
- 앱 코드(언어 확정 후)에도 같은 경계 검사를 따로 붙여야 한다. 아직 없다.
- 하나의 DB를 공유하므로 DB 장애/부하가 전체에 영향을 준다. 읽기 부하는 읽기 전용 복제본, 무거운 계산은 워커로 완화한다.

## 다시 검토할 신호

아래 중 하나가 생기면 해당 모듈을 서비스로 분리하는 것을 검토한다 (먼저 별도 워커 프로세스로 충분한지 확인).

- 조판/PDF 렌더의 CPU·메모리가 API와 따로 확장되어야 한다.
- 여러 팀이 독립 배포 주기를 요구한다.
- 특정 모듈이 DB 종류나 일관성 모델을 달리해야 한다 (예: 이미지 분석 결과를 별도 저장소로).
- `architecture.md`의 "알려진 예외" 표가 계속 늘어난다.
