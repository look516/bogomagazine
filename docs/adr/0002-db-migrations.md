# ADR-0002: Flyway 버전 마이그레이션 + 모듈별 반복 마이그레이션

- 상태: 채택
- 날짜: 2026-10-01

## 배경

초기 SQL은 "빈 DB에 처음부터 만드는" 스크립트였다. 이미 운영 중인 DB에는 적용할 방법이 없고, 사람이 어떤 파일을 어떤 순서로 실행할지 기억해야 했다. 이것이 휴먼 에러의 가장 큰 원인이었다.

## 결정

[Flyway](https://flywaydb.org) (OSS, 버전 13.8.1 고정, Docker 이미지로 실행)를 쓴다. 두 종류의 파일을 구분한다.

| 종류 | 파일명 | 용도 | 규칙 |
|---|---|---|---|
| 버전 | `V###__설명.sql` | 테이블/컬럼/인덱스 같은 **구조 변경** | **한 번만 적용. 합쳐진 뒤에는 절대 수정 금지.** 변경은 다음 번호의 새 파일 |
| 반복 | `R__###_모듈_설명.sql` | **함수, 뷰, 트리거** | 자유롭게 수정. 내용이 바뀌면 다음 migrate 때 자동 재적용. 번호 순서로 적용 |

- `V001__baseline.sql`은 현재까지의 스키마 전체다.
- 반복 파일 이름에는 소유 모듈을 넣는다 (`R__020_issues_lifecycle`). 한 파일이 여러 모듈에 걸치면 나눈다.
- 롤백(down) 마이그레이션은 두지 않는다. **앞으로만(forward-only)** 고친다. 잘못된 변경은 새 마이그레이션으로 되돌린다.
- `flyway clean`(DB 전체 삭제)은 비활성화한다. 로컬 초기화는 `./scripts/db.sh reset`만 쓴다.
- 개발용 시드(`db/seed/dev.sql`)는 마이그레이션이 아니다. 운영 DB에 적용하지 않는다.

## 이유

- 함수/뷰는 자주 바뀐다. 버전 파일로 두면 수정할 때마다 번호가 늘어나고 "현재 정의"를 한눈에 볼 수 없다. 반복 파일은 파일 자체가 항상 현재 정의다.
- 테이블 변경은 순서가 중요하고 되돌릴 수 없으니 버전 파일로 고정하는 편이 안전하다.
- 반복 파일이 `DROP ... IF EXISTS` + `CREATE`로 쓰여 있어 여러 번 적용해도 안전하다.

## 자동 방어

| 사고 | 막는 곳 |
|---|---|
| 합쳐진 V 파일을 수정 | `scripts/check-migrations.sh` (pre-commit, PR CI) + `flyway validate` (체크섬) |
| 같은 번호의 V 파일 두 개 | 〃 |
| 번호가 더 작은 V 파일을 뒤늦게 추가 | 〃 (기존 DB에서 적용이 거부되기 때문) |
| 파일 이름 오타 | 〃 + `FLYWAY_VALIDATE_MIGRATION_NAMING` |
| 셸 스크립트/훅이 CRLF 가 되어 Linux CI 에서만 실패 (`set: pipefail: invalid option name`, 재현 확인) | `.gitattributes` 로 LF 고정. 참고: Flyway 체크섬은 줄바꿈과 무관함을 확인했다 (CRLF 사본으로 validate 통과) |
| 새 테이블에 소유 모듈을 안 적음 | `db/tests/architecture.sql` T90 |

## 큰 테이블에 인덱스를 추가할 때 (실제로 겪은 함정)

운영 중인 큰 테이블에는 쓰기를 막지 않도록 `CREATE INDEX CONCURRENTLY`를 써야 한다 (PostgreSQL 마이그레이션 린터 squawk도 이를 요구한다).
그런데 Flyway 기본 설정에서는 **이 마이그레이션이 영원히 멈춘다.** 재현했다: Flyway의 다른 연결이 트랜잭션을 쥔 채 대기하고, `CONCURRENTLY`는 그 트랜잭션이 끝나기를 기다린다.

- 해결: `FLYWAY_POSTGRESQL_TRANSACTIONAL_LOCK=false` (docker-compose.yml에 적용됨). 이 상태에서 Flyway는 해당 마이그레이션을 `[non-transactional]`로 자동 처리한다. 적용 확인: 22ms, 인덱스 유효, 멈춘 세션 없음.
- **운영 배포에서도 같은 값을 반드시 써야 한다.** 빠뜨리면 배포가 멈춘다.
- 트랜잭션 밖에서 실행되므로 **한 파일에 한 문장만** 둔다. 중간에 실패하면 되돌려지지 않는다. 실패 시 `INVALID` 상태로 남은 인덱스는 지우고 다시 시도한다.

## 감수하는 점

- Flyway 이미지가 크다(약 1.1GB). 첫 실행에서 내려받는다.
- 반복 마이그레이션은 파일 이름의 번호 순서로 적용된다. 다른 파일의 객체를 **생성 시점에** 필요로 하는 SQL 함수/뷰를 추가하면 번호를 맞춰야 한다. (plpgsql 함수 본문은 실행 시점에 해석되므로 해당 없음)
  현재 파일들은 **순서에 의존하지 않음을 확인했다**: 반복 마이그레이션 7개를 역순과 무작위 순서로 적용해도 테스트가 전부 통과하고, 이미 적용된 DB에 2번 다시 적용해도 오류가 없다.
- **plpgsql 함수 본문은 PostgreSQL이 검사하지도 의존성을 추적하지도 않는다.** 컬럼 이름을 바꿔도 마이그레이션은 성공하고 해당 함수를 실행하는 **테스트에서만** 실패한다(재현 확인). 뷰는 추적한다(쓰는 컬럼을 지우려 하면 거부). 그래서 함수마다 테스트가 있어야 하고, 정적 검사(`plpgsql_check`) 도입을 TODO로 둔다.
- 운영 DB에 적용하기 전 백업과 절차는 아직 정해지지 않았다. TODO.md 참고.
